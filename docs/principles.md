# PRINCIPLES.md

> 核心原则（Principles）：回答「AceNvim 为什么这样设计」。

本文档是 AceNvim 核心原则的唯一事实来源。其他文档可以引用原则名称并说明其在特定领域的应用，但不重复定义原则。

## Feature-Centric — 以功能为中心

围绕用户实际工作流组织系统，而不是围绕插件组织系统。

- Feature 是架构的基本组织单元。
- 一个 Feature 应具有清晰、独立的职责。
- Feature 内部可以包含原生实现、插件适配、快捷键、命令等。
- Feature 之间保持低耦合，避免相互依赖内部实现。

> 原则：先定义功能，再选择实现。

## Native First — 原生能力优先

优先使用 Neovim 0.12+ 的原生 API 和内置工作流。

只有当原生能力存在明确缺口时，才引入额外抽象或插件，引入插件时必须能够回答：

- 原生方案是什么？
- 原生方案具体缺少什么？
- 插件解决了什么问题？
- 插件失败后如何降级？

> 原则：插件是能力补充，而不是架构基础。

## Explicit — 显式优于隐式

优先选择行为明确、依赖明确、生命周期明确的设计。

- 显式配置优于隐式约定。
- 显式依赖优于全局共享状态。
- 显式生命周期优于隐藏初始化。
- 显式错误处理优于静默失败。
- 显式 Feature 边界优于跨模块调用内部实现。

> 原则：代码应该让人一眼看懂，而不是依赖“猜”。

## Simple — 简洁优先

只引入解决实际问题所必需的复杂度。

- 不为未来可能出现的需求提前设计复杂抽象。
- 不为了“架构完整”而增加层级。
- 不为了统一而统一。
- 不重复实现 Neovim 已经提供的能力。
- 优先选择最简单、可维护的解决方案。

> 原则：能简单解决的问题，不用复杂方案解决。

## Stable — 稳定优先

优先保证行为稳定、升级可控和局部故障隔离。

- Feature 之间尽量相互隔离。
- 单个插件异常不应导致整个配置不可用。
- 外部能力失败时提供合理降级。
- 避免不必要的全局状态。
- 避免对插件内部实现产生强依赖。
- 升级依赖时优先考虑兼容性和回退路径。

> 原则：局部问题不应演变成系统问题。

## Observable — 可观测

系统的状态、错误和运行条件应该能够被发现和诊断。

至少能够回答：

- Feature 是否启用？
- Feature 是否正常初始化？
- 依赖是否存在？
- 为什么没有生效？
- 发生了什么错误？
- 当前使用的是原生能力还是插件能力？

因此：

- 外部依赖失败时给出明确反馈。
- 错误不能无声吞掉。
- 状态尽可能局部化、可查询。

> 原则：出了问题，要能够知道问题在哪里。
